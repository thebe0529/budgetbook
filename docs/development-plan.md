# 개인 맞춤 가계부 개발계획서 v0.1 (확정 정책 반영)

작성일: 2026-09-28

## 1. 목표와 범위

Actual Budget의 빠른 계좌별 거래 입력, 분할 거래, 온/오프 버짓, 월별 예산, 규칙과 입력 금액 필드의 사칙연산, 로컬 우선 PWA 경험을 기본 기능으로 구현한다. 추가로 사용자 정의 자산·부채 계정 그룹, 회계형 명세서, 직접 호출 가능한 수신 REST API, 신용카드 청구 및 미래 현금흐름 분석을 제공한다. 초기 배포는 개인 또는 가족이 자체 서버(예: 시놀로지 NAS)에 설치하는 방식을 전제로 한다. 개발 방식은 독립 제품을 기본으로 확정한다. Actual의 일부 코드는 기능별 기술 검증 후 선택적으로 재사용한다. 제품 전체를 Actual 포크로 유지하지 않는다.

### 설계 원칙

- **하나의 원장, 여러 관점:** 계좌 잔액·예산·재무제표·카드 청구 전망은 같은 확정 거래와 별도의 예측 데이터에서 계산한다.
- **거래와 현금흐름을 구분:** 카드 사용일의 소비와 결제일의 현금 유출을 중복 비용으로 잡지 않는다.
- **로컬 우선:** 오프라인에서도 입력·조회·편집하고 연결 후 변경을 동기화한다. 서버로 들어온 단축어 거래도 연결 후 내려받는다.
- **회계형 보고서는 개인 재무관리 목적:** 기업회계기준 재무제표와 동일한 공시 보고서라고 표시하지 않는다.

## 3. 핵심 데이터·회계 모델

- `Household/Book`(가계부) → `Member`(역할) → `AccountGroup` → `Account`(자산/부채, 온/오프 버짓, 카드 옵션).
- `Transaction`(날짜, 거래처, 상태, 원천, 외부 식별자) → `Posting`(계정, 증감 금액) 및 `Allocation`(예산·보고 카테고리, 금액). 거래 입력 화면은 분할 행으로 보이되 내부의 금액 정합성은 원자적으로 검증한다.
- 복식부기 분개는 차변·대변 합계를 항상 일치시킨다. 손익계산서는 수익/비용 계정을 집계하며, 현금·카드·이체·기초 잔액과 손익 항목을 분리한다. 자산 가치 변동을 자동 평가하거나 평가손익을 발생시키지 않는다.
- `BudgetCategory`와 회계 보고용 `ReportCategory`는 분리해서 연결한다. 보통예금은 계정 그룹이고 식비는 소비 카테고리이며, 같은 단어 ‘카테고리’라도 서로 다른 차원이다.
- 카드의 `CardPurchase`/`InstallmentPlan`/`InstallmentDue`는 확정 거래와 예정 지급을 연결한다. 예정액은 실제 원장을 증가시키지 않으며 확정 청구·결제와 매칭되면 예측에서 제거한다.
- `Schedule`, `ForecastScenario`, `ImportEvent`(원문·수신시간·해시·상태), `ParserRule`(우선순위·버전·테스트 예시), `AccountMapping`, `SyncOperation`, `AuditEvent`를 별도 관리한다.
- 금액은 통화별 최소 단위 정수로 보관한다. 초기 기본 통화 KRW; 다중 통화·환율 평가가 필요하면 별도 범위로 확정한다. 일자 기준과 카드 결제일 규칙은 Asia/Seoul로 고정해 시작한다.

### 카드 거래 예시

10월 10일에 카드로 120,000원을 3개월 무이자 결제하면 10월에 소비 120,000원과 카드 부채 120,000원이 잡힌다. 11·12·1월 결제 예정표에는 각각 40,000원의 현금 유출을 보여준다. 실제 11월 카드대금 40,000원을 납부할 때는 예금과 카드 부채를 각각 40,000원 줄이고, 11월 소비 40,000원은 새로 기록하지 않는다. 할부 수수료가 있다면 비용과 현금 지급을 별도 처리한다. 카드사 이용 기간에 따른 첫 청구월, 부분취소·환불·조기상환은 명시적으로 재계산한다.

### 월말 일괄 조정

누락된 거래를 기간별 조정 목록으로 등록하거나 다수 행을 가져와 미리보기 후 하나의 배치로 확정한다. 각 조정 행은 발생일·사유·차변/대변 계정·금액·손익 반영 여부·원천을 기록하고 차변 합계와 대변 합계를 맞춘다. 예를 들어 누락된 현금 식비 20,000원은 식비 비용 증가/현금 감소로 입력한다. 잔액 차이의 원인을 모를 때는 임의로 수익·비용에 넣지 않고 **미분류 조정 계정**에 보류해 나중에 재분류한다. 일괄 조정은 확정 전 잔액·손익·예산 영향 미리보기, 확정 후 배치별 감사 이력 및 역분개/재분류를 제공한다. 확정한 과거 기간을 고치면 비교 보고서를 다시 계산한다.

### 보고서 산식과 범위

- 재무상태표: 특정 기준일의 계정 잔액을 현금성 자산·그 외 자산·카드/대출 부채로 집계하고 순자산을 산출한다. 오프버짓 자산/부채도 기본 포함하고 필터로 제외할 수 있다.
- 손익계산서: 복식부기 수익/비용 계정의 기간 증감과 순손익을 보여준다. 계좌 간 이체·카드대금 지급·기초 잔액은 손익에서 제외한다. 누락분은 승인된 조정 분개만 반영한다. 개인 가계용 기준을 안내하며 자산 평가손익·법인용 결산 항목은 자동 처리하지 않는다.
- 현금흐름표형 명세서: 선택한 현금성 계좌의 실제 입출금을 영업/투자/재무/내부이체 중 사전 정의한 기준으로 분류한다. 현금성 계좌 간 이체는 통합 보기에서 제거한다. 카드 구매는 구매 시 현금 유출이 아니며 카드 결제일에 현금 유출로 반영한다.
- 예측 보고서: 확정 잔액에 일정·카드 청구·임시 시나리오를 더한 별도 층이다. 실제 명세서와 혼합하지 않는다.

## 4. 시스템 구성

| 구성 | 권장 설계 |
| --- | --- |
| PWA 클라이언트 | TypeScript/React 계열, 계좌 목록 가상 스크롤·키보드 편집, IndexedDB의 로컬 원장/변경 큐, Service Worker 오프라인 캐시 |
| 애플리케이션 서버 | TypeScript/Node.js의 REST API 및 동기화 서비스. 공통 도메인 검증·보고서 계산·파서 관리. OpenAPI 문서 생성 |
| 서버 저장소 | NAS의 Docker Compose로 운영하고 DB·첨부·설정을 영속 볼륨에 보관한다. DB 엔진은 원장·동기화 기술 검증 후 PostgreSQL 또는 SQLite/WAL 중 확정한다 |
| 인증 | Pocket ID OIDC Authorization Code + PKCE, 서버 세션과 CSRF 방어, issuer/audience 검증, `sub` 기반 사용자 매핑. 이메일만으로 계정 연결 금지 |
| 백그라운드 작업 | 수신함 파싱·반복 일정 생성·카드 청구 예측·동기화 재시도. 재시도 가능한 작업마다 idempotency 키 적용 |
| 배포·백업 | NAS Docker Compose와 HTTPS 역방향 프록시. 앱 설정에서 백업 시간·보관 개수·Google Drive 연결 관리. DB 일관성 있는 스냅샷과 첨부·설정을 묶어 기본 매일 1회 백업 |

브라우저가 오프라인일 때는 재인증이 불가능하므로, 신뢰 기기에서 마지막 온라인 인증 확인 시각으로부터 최대 30일 동안 로컬 열람·편집을 허용한다. 기한이 지나면 재인증 전 편집과 동기화를 제한하고 로컬 변경은 보존한다. 온라인 상태로 돌아오면 사용자·권한·기기 폐기 여부를 확인한 뒤 동기화한다. 오프라인 기기는 서버에서 즉시 차단할 수 없다는 한계를 안내하고, 가족별 로컬 데이터 분리와 기기 저장소 보호를 적용한다. 단축어는 사용자의 브라우저 로그인 세션 대신, 채널별 범위 제한 API 토큰을 사용한다. 앱에서 토큰 생성·폐기·마지막 사용 시각을 관리하고 서버에는 해시로 저장한다. API에서 받은 데이터는 서버 원장에 반영되고 클라이언트에 동기화된다. 기기와 서버의 동시 수정은 필드별 자동 병합보다 거래 단위 버전 검사와 충돌 검토함을 우선한다.

### REST 수신 흐름

`POST /api/v1/import-events`에 채널 토큰, 원천 계정 ID, 발생 시각, 원문 메시지/구조화 필드, 외부 거래 ID 및 `Idempotency-Key`를 받는다. `202 Accepted`와 수신 ID를 반환한다. 원문 저장 → 채널/계좌 식별 → 버전 있는 파서 규칙 적용 → 금액·일자 유효성 검사 → 외부 ID/지문 중복 검사 → 기존 거래 매칭 → 검토함 또는 거래 확정 순으로 처리한다. `GET /api/v1/import-events/{id}`로 처리 상태와 오류를 확인하고 재처리할 수 있다. 앱 화면에서 은행별 계좌 매핑, 정규식·키워드·구조화 필드 규칙의 테스트/우선순위/활성화를 관리한다. 로그와 오류 응답은 카드번호·계좌번호·문자 원문을 가린다.

신한·하나 수집을 먼저 연동하고 기존 은행→별도 API→Actual 전달 과정은 초기에는 새 REST API 어댑터로 대체한다. 기존 수집기와 API 코드가 제공되면 실제 요청 형식에 맞춰 데이터 계약과 이행 절차를 확정한다.

## 5. 개발 단계 및 완료 기준

1. **기반/검증:** 실제 사용 흐름과 Actual 내보내기 샘플 수집, 거래·분할·이체·온/오프 예산·카드 회계 규칙 확정, 화면 와이어프레임, NAS 설치 구조 결정. 대표 거래 20~30건으로 기대 잔액·보고서 결과표 작성.
2. **MVP 원장과 예산:** Pocket ID 로그인과 가족 초대·기본 권한, 가계부·계좌 그룹, 계좌별 엑셀형 입력, 분할·이체·대사, 월별 예산, 기본 규칙, 기초 잔액. 잔액 검증과 Actual CSV 가져오기 제공.
3. **동기화 기술 검증 및 로컬 우선 PWA:** 일반 거래 수정·할부 예정액 변경·두 기기 동시 수정·서버 API 수신 거래의 기기 반영을 Actual의 동기화 코드로 검증한다. 새 원장과의 결합, 업그레이드 가능성, 충돌 처리 비용을 기록해 부분 재사용 또는 자체 구현을 결정한다. 이후 오프라인 입력, 변경 큐, 서버 수렴, 기본 일일 백업·복원, iPhone 홈 화면 설치를 검증한다.
4. **수신 API:** 아이폰 단축어 예제, 채널 토큰, 신한·하나 우선 파서, 계좌 매핑 UI, 원문 검토함·중복 제거, 기존 수집기 이행.
5. **카드·보고서:** 카드사별 청구 규칙/할부·취소·부분납부, 재무상태표·수입지출·실제 현금흐름표와 원거래 드릴다운.
6. **예측·입력 계산·운영 고도화:** 일정, 현금흐름 시나리오, 금액 입력 필드 사칙연산, CSV/Excel 추출, 가족 세부 권한 관리, 백업 주기 설정 및 Google Drive 연결·복원, 성능·접근성 검증. 복잡한 수식 엔진은 도입하지 않는다.

단계별 핵심 자동 검증: 원장 합계와 이체 정합성, 오프버짓 영향, 동일 API 요청 재전송, 카드 사용·청구·결제·취소, 오프라인 양쪽 기기의 동일 거래 수정, 백업 복원 후 잔액과 수신 이력 일치. 실제 사용 데이터로 병행 운영하여 월말 잔액과 보고서 숫자를 대조한 후 전환한다.

## 6. 추가 반영한 누락 위험과 정책 초안

1. **초기 잔액과 이관:** Actual의 모든 데이터를 동일하게 옮길 수 있다고 가정하지 않는다. 계좌·거래·분할·카테고리·예산·규칙·일정별 가져오기 가능 범위를 사전 검증하고, 원본 내보내기와 읽기 전용 보관을 남긴다.
2. **중복 수신·대사:** 단축어 알림, 은행 CSV, 수기 입력이 같은 거래를 가리킬 수 있으므로 출처별 식별자, 유사 금액/일자 매칭, 승인된 병합 이력을 둔다.
3. **거래 변경 이력:** 특히 대사 완료 거래의 변경을 경고하고 취소/정정으로 추적 가능한 이력을 남긴다. 카드 부분취소와 환불은 원거래를 참조한다.
4. **가족 공유:** 가계부 소유자와 가족 구성원의 초대·제거·권한을 제공한다. 기본은 가족 가계부 전체 공유로 하되, 개인 전용 계좌가 필요할 경우 해당 계좌 거래·검색·보고서·로컬 캐시까지 권한 범위를 일치시킨다. 공유 장부 변경 이력에 작업자를 남긴다.
5. **백업과 보안:** 기본 매일 1회 백업, 설정 가능한 실행 시각·주기·보관 개수 및 Google Drive 저장 옵션을 제공한다. DB·첨부·설정의 일관된 백업을 NAS에 만든 뒤 선택적으로 암호화해 Drive에 업로드하고 성공/실패·마지막 정상 백업을 표시한다. 복원은 별도 데이터에서 주기적으로 검증한다. Drive 연결은 별도 Google OAuth로 처리하며 Pocket ID 로그인과 혼동하지 않는다. 연결 해제·토큰 만료·용량 부족 시 로컬 백업을 유지하고 실패를 알린다. 토큰 회전, HTTPS, NAS 장애·인증 서버 장애 시 동작 정책을 문서화한다.
6. **예측 가정:** 카드 이용 기간/청구일의 카드별 차이, 공휴일/주말 처리, 급여 변동, 계좌 간 이체, 예산 배정과 실제 현금의 차이를 명시한다.
7. **범위 관리:** 투자 시세, 대출 상환표, 복수 통화, 영수증 OCR, 은행 자동 로그인/스크래핑은 1차 필수 기능에서 제외하고 별도 요구 검토 대상으로 둔다.

## 7. 확정 정책 및 구현 세부 선택

- **개발 방식(확정):** 독립 제품과 자체 원장·API·카드·보고서를 개발한다. Actual의 동기화 코드는 4개 필수 시나리오를 포함한 기술 검증을 통과할 때만 범위를 한정하여 재사용한다. 거래 입력과 예산은 사용 경험을 참고해 독립 구현한다. 재사용한 코드의 버전·출처·수정 범위·원 라이선스 고지를 기록한다.
- **보고 기준(확정):** 복식부기 기반 개인 가계용 손익계산서. 자산 평가손익은 자동 처리하지 않으며 누락 항목은 근거를 남긴 일괄 조정 분개로 반영한다. 재무상태표는 오프버짓 계정을 기본 포함하되 조회 필터를 제공한다.
- **운영 정책(확정):** 가족 공유, NAS Docker 컨테이너 운영, 신뢰 기기 마지막 온라인 인증 후 30일 오프라인 사용, 매일 1회 기본 백업과 앱 설정에서 주기 변경, Google Drive 선택 연동. DB 엔진·백업 보관 개수·역할별 세부 권한은 구현 단계에서 확정한다.
- **수식 범위(확정):** 금액 입력 필드에서 사칙연산과 괄호를 계산하여 결과 금액만 저장한다. Excel 함수·셀 참조·자동 재계산은 구현하지 않는다. 따라서 HyperFormula 도입을 전제로 하지 않는다.
